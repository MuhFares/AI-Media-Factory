## A. Executive conclusion

The platform is operational and governed, but the Owner-facing experience remains partly engineering-console oriented. Proven capabilities (durable workflows, scoped approvals, lineage, UNKNOWN-cost semantics, strategic versioning, audited gates) are real, yet too many surfaces expose the implementation model — technical IDs as primary labels, raw JSON, browser `alert()` validation, API-operation naming — instead of a business-first Owner product. V1.1 must translate, never weaken: governance, lineage, auditability, and historical truth stay intact under progressive disclosure (business meaning → operational details → technical/audit details; Level 3 is never removed).

## B. What worked well (must be preserved)

- Real durable workflow state visible; `revision_required` displayed honestly (not prettified).
- Pending Owner attention visible (1 pending visual gate with correct WORKFLOW_GATE meaning).
- Decision != Authority visible; validation approval distinct from production/publication authority; publication blockers visible (`NO_PRODUCTION_APPROVAL`, `NO_PUBLIC_PUBLISH_APPROVAL`, `TARGET_ACCOUNT_NOT_RESOLVED`).
- UNKNOWN costs preserved, never summed as zero (FREE vs UNKNOWN distinct).
- Real worker/queue state visible (1 live worker, heartbeat, build parity, queue depth, failures not hidden).
- Strategic ACTIVE/SUPERSEDED/PROPOSED visible; readiness INCOMPLETE honest; context preview side-effect-free; task-aware strategic context visible.
- Pre-strategic executions correctly show no strategic snapshot ("No strategic snapshots reference this artifact (pre-layer executions carry none)") — correct history, do NOT backfill.
- Configuration inheritance/source visible; final media exists and is visible; human gates real and audited; localhost/no-auth limitation disclosed in UI.

## C. Owner UX findings (stable IDs — never renumber)

### PROJECT HUB
- **UX-HUB-001** — QA/test fixture projects (observed: `strat-qa-…`) appear in the normal Active Projects list. They must remain in persistence/audit evidence but must not appear as normal Owner projects by default. Need business project cards + filtering/status.

### DASHBOARD
- **UX-DASH-001** — Real data present and trustworthy, but dashboard is not action-oriented. Need: current project health, lifecycle position, Owner attention, next recommended/required action, publication readiness, strategic readiness. Technical IDs become secondary metadata.

### CONTENT PIPELINE
- **UX-PIPE-001** — Surface behaves like a durable workflow database viewer (technical workflow IDs primary, raw statuses/jobs exposed). Need lifecycle visualization (Idea → Research → Brief → Script → Visual Plan → Production → QA → Owner Review → Ready → Published).
- **UX-PIPE-002** — Canonical path not visually distinct from failed/superseded/historical/validation-only branches. Observed confusion: video/WAN stages may read pending/failed while canonical final media exists via later governed validation/resume paths. Fix by explicit canonical-vs-historical representation. Do NOT falsify historical status.

### AGENTS
- **UX-AGENT-001** — SET override without rationale uses browser `alert("Rationale required")`. Need inline validation + confirmation modal.
- **UX-AGENT-002** — Raw configuration JSON in Owner UI; dense technical provider/model/source representation. Need business-readable rendering with Advanced details retained.
- **UX-AGENT-003** — Need business-readable agent cards/table (effective provider, model, source, strategic context, recent runs, cost semantics) + safe configuration editor. Historical pre-layer "none" state must remain unchanged in meaning.

### COMMAND ROOM
- **UX-CMD-001** — UX resembles API/runtime console: raw operation names (`ASK_AGENT`, `MULTI_AGENT_REVIEW`, `START_GOVERNED_TASK`), large HTML multi-select, technical command IDs primary, limited pre-execution explanation. Need Owner-instruction-first flow. Do not weaken governed runtime.
- **UX-CMD-002** — Need human-readable modes (Ask one specialist / Get multiple expert opinions / Start complete governed workflow) + execution preview (agents, effective provider/model, strategic context, authority/gates, side-effect expectation, cost semantics). Recent commands: human-readable titles first, IDs second.

### APPROVAL CENTER
- **UX-APPR-001** — Technical approval IDs dominate; rationale flow is low-level. Need human-readable subject (what decision means, what authority it grants AND does not grant, risk, affected workflow/entity) + confirmation modal + advanced technical details. Never collapse Decision and Authority.
- **UX-APPR-002** — High-impact actions (especially publication-adjacent authority) need a clearer confirmation experience proportionate to risk.

### ARTIFACTS & LINEAGE
- **UX-ART-001** — Strong forensic tool, weak asset workspace. Need business asset categories first (Final Video, Script, Research, Brief, SEO Package, Brand/Visual Direction, Images/Scenes, Narration, Reviews/QA, Publication Validation); technical artifacts under Advanced/Lineage. Lineage stays complete.
- **UX-ART-002** — Final media should be easy to find and preview/play if safely possible.
- **UX-ART-003** — Translate "No strategic snapshots reference this artifact (pre-layer executions carry none)" into Owner-readable language; retain technical detail. Do NOT backfill fake context.

### STRATEGY (HIGH PRIORITY)
- **UX-STRAT-001** — Owner cannot comfortably inspect proposed entity payload/evidence (raw JSON, weak source review).
- **UX-STRAT-002** — No structured difference from current effective state (deterministic diff missing in UI).
- **UX-STRAT-003** — Proposal creation requires compact JSON; source refs require manual comma-separated technical input. Need structured business forms (raw JSON only as advanced path).
- **UX-STRAT-004** — Activation requires manually copying entity ID + approval ID between steps. Target journey: Proposal → Inspect → Evidence → Compare/Diff → Owner Decision → Exact Authority → Activate → Effective State → Preview changes, without manual ID plumbing (exact governed authority underneath unchanged).

### COSTS
- **UX-COST-001** — Semantics correct; presentation raw (`{"UNKNOWN":99,"FREE":24}`). Need Owner-readable cards/breakdowns; raw data under Advanced.

### HEALTH
- **UX-HEALTH-001** — Real state visible but build hashes/historical failures too prominent. Need Owner-level summary (platform status, worker health, parity, queue, running work, recent incidents, provider health, action required); failures grouped/summarized, never hidden.

### PROJECT SETTINGS
- **UX-SET-001** — Gate enable/disable needs explicit confirmation + rationale UX explaining future-workflow impact, no auto-release of pending approvals, and auditability. Semantics unchanged.

### GLOBAL SYSTEM
- **UX-GLOB-001** — Technically correct but minimal. Target: AMF Mission Control (platform, workers, queue, providers, models, projects, incidents, parity, cost posture). Keep localhost/no-auth warning until resolved.

### CROSS-CUTTING
- **UX-X-001** — Technical IDs too often primary labels (workflows, approvals, artifacts, entities).
- **UX-X-002** — Raw JSON appears in Owner surfaces.
- **UX-X-003** — Browser `alert()` used for validation.
- **UX-X-004** — Engineering terminology dominates some workflows; business summary must be primary, technical details secondary.
- **UX-X-005** — Consistent dark shell exists but information hierarchy needs strengthening.

Binding cross-cutting rules: historical truth stays accessible; no cosmetic change may hide UNKNOWN/failure/pending states; no UX change may weaken approval authority; Owner needs no SQL/PowerShell/DB/ID knowledge for normal operation.
